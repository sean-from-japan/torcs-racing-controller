# Corkscrew 自律走行コントローラ — CMA-ES + 残差ネットワーク

レーシングシミュレータ [TORCS](https://sourceforge.net/projects/torcs/) の自律走行コントローラです。Corkscrew コースのラップタイムを **261.42秒から106.63秒** へ、**59%** 短縮しました。

IBM AI Racing League のために作ったもので、参加校の一つで実施されたグループプロジェクト科目のクライアント課題です（2026年）。このリポジトリに入っているのは**私個人のエージェント**であって、チームが提出した統合版ではありません。詳しくは[担当範囲とチームの境界](#担当範囲とチームの境界)をご覧ください。大学名と科目コードは意図的に伏せています。確認に必要でしたら個別にご連絡ください。

技術文書の本体は英語の [README.md](README.md) です。この文書は要点だけをまとめたものですので、実装の詳細はリンク先をご覧ください。

## 計測した結果

| | ラップタイム | ベースライン比 |
|---|---|---|
| ルールベースのベースライン（`snakeoil`） | 261.422秒 | — |
| CMA-ES コントローラ（8パラメータ + s35 上限） | 108.692秒 | −58.4% |
| ＋ 残差ネットワーク（ARS、6時間） | 106.630秒 | −59.2% |

評価条件は、Corkscrew（1周3,608m、コーナー半径は480mから14mまで）における、リーグ標準のレース設定でのウォームラップの最良タイムです。ウォームラップは2周目以降を指し、停止状態から始まる1周目は数えません。ベースラインの `snakeoil` は課題側から支給された固定のルールベース制御で、この261.42秒が上回るべき基準でした。

各段階の実測値は [`results/`](results/) にコミットしてあります。段階との対応は英語READMEの [Iteration timeline](README.md#iteration-timeline) と [Results](README.md#results) にあります。

## 担当範囲とチームの境界

このリポジトリの中身はすべて私が書きました。制御則、各段階の最適化の設定、失敗の診断、残差ネットワークとその学習ループ、評価を回す仕組みです。自分で書いていないものは [Attribution](README.md#attribution) に列挙しています。

プロジェクトは6人・英語のみのチームで、IBMがクライアントでした。**このリポジトリには私個人のエージェントしか入っていません。**ここに載せたラップタイムは私のコントローラ単体で出したものです。チームメイトのコード、チームの統合版、共同の成果物は含めておらず、チームメイトの名前も出していません。個人のエージェントはレースを完走しましたが、複数人の手法を組み合わせたチームの統合版は完走しませんでした。

## なぜ CMA-ES なのか

深層強化学習が想定される道筋で、6人中5人が方策勾配法（PPO、SAC）を選びました。私も強化学習のエージェントを先に作り、二つの障害を推測ではなく実測しました。一つは、ランダムに初期化した方策が数秒でコースを外れるため、序盤のロールアウトのほとんどが勾配の手がかりを出す前に終了することです。もう一つは、ロールアウト1回が実時間のシミュレータ1エピソードにあたり、収束には数千回、つまり1学期のプロジェクトに収まらない時間が必要だったことです。

そこで課題の立て方を変えました。1周を走りきれるコントローラはすでにあり、足りないのは調整でした。これは少数の連続パラメータに対するブラックボックス最適化であって、方策をゼロから学習する問題ではありません。[CMA-ES](https://en.wikipedia.org/wiki/CMA-ES) は微分を使わず、実行ごとにばらつく目的関数に強く、数十次元までなら効果的です。何より**すでに完走する方策から探索を始められる**ため、コースを外れない走り方を覚えるだけの段階に予算を使わずに済みます。

同じ考え方を全体に通しました。パラメータは現在の空間を使い切ってから増やし、各段階は前の段階の最良値から始めます。経緯は [Why CMA-ES, and not deep RL](README.md#why-cma-es-and-not-deep-rl) にあります。

## 設計で押さえた点

- **2パラメータずつ増やす** — どの改善がどの判断によるものか対応づけられるようにしました。段階ごとのパラメータと実測値は [Iteration timeline](README.md#iteration-timeline) の表にあります
- **不感帯 `D` の追加** — 124秒付近で頭打ちになった原因は、直線での横位置センサのノイズが微修正を誘発するジグザグでした。横方向の誤差が `D` を下回る間は無視する形にしたところ、CMA-ES が `D ≈ 0.083` を見つけ、走行ラインが直線的になって約2秒短縮しました。仮説が先にあり、CMA-ES が担当したのは調整だけです
- **区間ごとの前方注視ゲイン** — 全周で共通のゲインでは、半径18〜20mの最終ヘアピンへ速すぎる速度で進入します。区間を分けて進入側だけ別のゲインにすることで、他の区間を遅くせずに解決しました
- **s35 の断続的な衝突を、当て推量ではなく突き合わせで特定** — 最適化に入る前にコース定義を区間表へ変換してあったため（[`src/analyze_track.py`](src/analyze_track.py) → [`results/corkscrew_segments.json`](results/corkscrew_segments.json)）、衝突時の走行距離を照合できました。結果はすべて2,441mと2,461mの二つの左コーナー、つまりシケインに収まりました。対処は罰則項でも全体の減速でもなく、2,339〜2,510mの区間にだけ適用する速度上限 `C_s35 = 71.4 km/h` です。残り3,400mの時間を犠牲にしないための選択で、この段階だけで116秒から108.692秒になりました。診断の全体は [The s35 diagnosis](README.md#the-s35-diagnosis) にあります
- **残差ネットワークは置き換えではなく上乗せ** — 出力層をゼロ初期化しているため、最初の評価は調整済みコントローラそのものです（`test_zero_network_output_is_the_rule_controller` がこの性質を固定しています）。補正は0.2倍に制限し、学習対象は出力層の33パラメータだけにしました。評価1回が実際の1周にあたるため、探索空間を小さく保つ必要がありました。6時間の微調整で106.630秒です。詳細は [Residual NN + ARS](README.md#residual-nn--ars) にあります

## 動かし方

制御則は純粋な関数として [`src/controller.py`](src/controller.py) にまとまっていて、シミュレータもPyTorchもNumPyも要りません。46件のテストは標準のPythonだけで1秒以内に終わります。

```bash
python -m unittest discover -s tests
```

図と区間表の再生成も、シミュレータなしで動きます。

```bash
python src/make_figure.py
python src/analyze_track.py --xml /path/to/torcs/tracks/road/corkscrew/corkscrew.xml
```

実際に走らせる場合は、主催者が指定したコンテナを使う手順が確実です。コンテナエンジンと約25GBの空き容量が必要になります。

```bash
bash container/build.sh
bash container/run.sh --race
```

2026-09-02にApple SiliconのMacで実測したところ、ウォームラップの最良タイムは**108.538秒**でした（記録上の基準値は108.692秒です）。手元のTORCSに対して走らせる手順を含め、詳しくは [`container/README.md`](container/README.md) と [Reproduction](README.md#reproduction) をご覧ください。

## 再現できないこと

106.630秒を出した走行の、残差ネットワークの出力層の重み（`models/nn_ars_s35_best.pt`、33個）は**コミットされていません**。`*.pt` が `.gitignore` に入っていたためで、どちらのプロジェクトのリポジトリのどのブランチにも残っていません。したがって、**その特定の1回の走行をこのリポジトリから再現することはできません**。`run_eval.py` は取り繕わずにその旨を表示して終了しますし、図でもこの段階には成果物がないことを示しています。学習ループ自体はコミット済みの108.692秒の状態から通しで動きますので、改めて走らせれば別の重みと別のタイムに収束します。

レポートに載せた途中の二つの値（8パラメータの区間版の116.062秒と、フィニッシュ直線のスプリントの112.404秒）にも、コミットされた成果物がありません。上の表からは外してあります。ラップタイムはTORCSのビルド、ブリッジへの変更、レース設定に依存しますので、公開した数値の近くには来ても同じ値にはならないとお考えください。

## 制約

- **環境をコンテナ化していませんでした。** 開発は1台の機械の上で、手作業で修正したTORCSに対して行いました。コードは可搬で学習ループも動きますが、計測した環境は手順としてしか残っておらず、バージョン管理の外にあった学習成果物はそれと一緒に失われました。このプロジェクトで最初に直すならここです
- **1コース・1車種・1レース設定です。** すべてのパラメータは Corkscrew に合わせたもので、汎化の証拠は `results/` にありません
- **区間の境界は手で決めました。** 走行ラインの窓の端と残差の倍率0.2は手動で選び、探索したのはその内側の値だけです
- **適応度が1回の走行に基づいています。** 各候補は1エピソードのウォームラップの最良タイムで採点していますので、隣り合う段階の差の一部は実行ごとのばらつきです
- **判断の理由を結果と一緒に記録していませんでした。** ラップタイムは自動で残りましたが、各段階でパラメータを増やした理由は残りませんでした
- **学習用スクリプトは `controller.py` に合わせて書き直していません。** 各段階は最終的な制御則より前のもので、書き直すと実際に走らせたものと食い違います
