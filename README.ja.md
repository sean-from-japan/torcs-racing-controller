# Corkscrew 自律走行コントローラ — CMA-ES + 残差ネットワーク

レーシングシミュレータ [TORCS](https://sourceforge.net/projects/torcs/) の自律走行コントローラです。Corkscrew コースのラップタイムを **261.42秒から106.63秒** へ、**59%** 短縮しました。

IBM AI Racing League のために作ったもので、参加校の一つで実施されたグループプロジェクト科目のクライアント課題です（2026年）。このリポジトリに入っているのは**私個人のエージェント**であって、チームが提出した統合版ではありません。詳しくは[担当範囲とチームの境界](#担当範囲とチームの境界)をご覧ください。大学名と科目コードは意図的に伏せています。確認に必要でしたら個別にご連絡ください。

## TORCS と、採点されたもの

**TORCS** は車両モデルを持つオープンソースの3Dレーシングシミュレータです。タイヤの荷重とすべり、空力、変速機、燃料、ダメージまで扱います。2008年から Simulated Car Racing（SCR）という競技会の実行環境として使われていて、SCR用のパッチを当てると `scr_server` というドライバが追加されます。このドライバ自体は運転をしません。UDPのポートを開き、制御周期ごとにセンサ値を送り、返ってきた指令をそのまま車に適用するだけです。つまりコントローラはシミュレータとは別のプロセスで、言語も自由です。私のものはPythonで、通信を担当するのが `gym_torcs` というブリッジです。

**コントローラが見えるもの**は、制御周期ごとに届く1通のメッセージだけです。

| センサ | 内容 |
|---|---|
| `track[0..18]` | コース端までの距離を測る19本のレンジファインダ（メートル、200mで飽和） |
| `angle` | 車の向きとコース方向の差（ラジアン） |
| `trackPos` | 横方向の位置。0が中央、±1でコース端 |
| `speedX/Y/Z` | 車体座標系の速度（km/h） |
| `distRaced` | セッション開始からの走行距離（メートル） |
| `curLapTime`、`lastLapTime` | 計時 |
| `rpm`、`gear`、`wheelSpinVel`、`damage`、`fuel` | 駆動系と車両の状態 |

19本のビームは等間隔ではありません。ブリッジが要求している角度は `-45 -19 -12 -7 -4 -2.5 -1.7 -1 -0.5 0 0.5 1 1.7 2.5 4 7 12 19 45` 度で、分解能のほとんどを正面付近に割り当てています。`track[9]` はちょうど正面を向いたビームで、コースが最初に曲がっていく地点までの距離を返します。直線では飽和し、コーナーが近づくにつれて縮みます。後述する速度系の入力はこの1本だけです。センサの配置はここでは些末な条件ではなく、前方注視型のコントローラが自然な解になる理由そのものです。

**コントローラが出すもの**は、[−1, +1] の `steer` と、同じく [−1, +1] の符号つきスロットル1つです。正がアクセル、負がブレーキにあたります。変速はブリッジ側の速度しきい値に任せていて、コントローラは関与しません。指令は制御周期ごとに1回で、周期はシミュレーション時間で20msです（固定したイメージに入っているTORCSのソースの `RCM_MAX_DT_ROBOTS`）。108秒のラップならおよそ5,400回の判断になります。

**採点されたもの**は、Corkscrew での**ウォームラップの最良タイム**です。1周目はグリッド上の停止状態から始まるので数えず、計測対象は2周目以降、つまり速度が乗った状態の1周です。走行は単独のプラクティスで、対戦相手も他車もいません。Corkscrew は1周3,608m、コーナー半径は480mから14mまで幅があります。

課題側から支給されたベースラインの `snakeoil` は固定のルールベース制御で、操舵則は `steer = angle × 10/π − trackPos × 0.10` がすべてです。これに速度上限と簡易な自動スロットルが付きます。このコントローラのタイムが261.42秒で、上回るべき基準でした。

## なぜ CMA-ES なのか

深層強化学習が想定される道筋で、6人中5人が方策勾配法（PPO、SAC）を選びました。私も強化学習のエージェントを先に作り、二つの障害を推測ではなく実測しました。一つは、ランダムに初期化した方策が数秒でコースを外れるため、序盤のロールアウトのほとんどが勾配の手がかりを出す前に終了することです。もう一つは、ロールアウト1回が実時間のシミュレータ1エピソードにあたり、収束には数千回、つまり1学期のプロジェクトに収まらない時間が必要だったことです。

そこで課題の立て方を変えました。1周を走りきれるコントローラはすでにあり、足りないのは調整でした。これは少数の連続パラメータに対するブラックボックス最適化であって、方策をゼロから学習する問題ではありません。何より**すでに完走する方策から探索を始められる**ため、コースを外れない走り方を覚えるだけの段階に予算を使わずに済みます。

同じ考え方を全体に通しました。パラメータは現在の空間を使い切ってから増やし、各段階は前の段階の最良値から始めます。

## CMA-ES の中身と設定

[CMA-ES](https://en.wikipedia.org/wiki/CMA-ES) はパラメータベクトルの上に多変量正規分布を1つ持ち、世代ごとに次の4つを行います。

1. **サンプリング** — `N(m, σ²C)` から λ 個の候補ベクトルを引きます。平均 `m` が現時点の見込み、`σ` が全体の歩幅、共分散 `C` がどの方向、どのパラメータの組み合わせを探る価値があるかを表します
2. **評価** — 候補を1つずつ走らせます。ここでは1回がTORCSの実走行にあたるため、λ は小さく取らざるを得ません
3. **順位づけ** — 適応度で並べ替え、上位 μ = λ/2 を残します。使うのは**順位だけ**で、ラップタイムの値そのものは更新に入りません
4. **更新** — 上位 μ の重みつき平均へ `m` を動かし、改善が出た方向へ `C` を伸ばし、`m` が進んできた経路の長さから `σ` を調整します。一貫して同じ向きに進んでいれば歩幅を広げ、行きつ戻りつしていれば縮めます

この問題に合っているのは3番目の性質のためです。更新が順位だけで決まるので、秒単位のばらつく目的関数をそのまま使えます。報酬の設計も正規化も微分可能なシミュレータも要りません。加えて共分散の適応が問題のスケールを学習してくれます。操舵ゲインと、メートル単位の区間境界とを同じベクトルに入れて探索する以上、これは実用上の要件でした。

段階4（[`src/train_cma_sector.py`](src/train_cma_sector.py)）の設定は次のとおりです。

| 設定 | 値 | 理由 |
|---|---|---|
| 集団サイズ λ | 8 | 8次元に対するライブラリ既定値の10より小さくしています。1回の評価が4周の実走行ですので、集団サイズは次元数ではなく時間の予算で決まります |
| 初期平均 | 前段階の122.060秒の解 | ランダムな初期化はしません。各段階は必ず完走できる方策から始めます |
| 次元ごとの σ | `[0.07, 0.013, 1.5, 0.013, 0.00016, 0.016, 0.20, 80.0]` | パラメータの大きさが5桁違います（`T ≈ 0.009` に対して `switch_dist ≈ 3,000`）。歩幅がスカラー1つだと、片方が動かないか、もう片方がコース外へ飛びます。調整済みの6つには狭く、新しい2つには広く取りました |
| 箱型の制約 | 例：`switch_dist ∈ [2700, 3400]`、`K_final ∈ [0.3, 2.0]` | 意味のある値に探索を閉じ込めます。区間の切り替え点はs45のコーナーとs48のヘアピンの間にしか置けず、`K_final` の上限は効果が消える値です |
| 予算 | 8時間、およそ50〜60世代 | 世代ごとにチェックポイントを取り、中断しても最初からやり直さずに再開します |

適応度の定義は読む価値があります。ラップタイムは1周を走り終えて初めて存在する量だからです。

```python
def _fitness(warm, cold, dist, steps):
    if warm is not None:              # ウォームラップを完走：そのまま採点
        return warm
    if cold is not None:              # 停止発進の1周目だけ完走
        return cold * 1.2
    if dist > 500 and steps > 100:    # 衝突：そこまでのペースから外挿
        return (steps * 0.02) * TRACK_LAP_M / dist
    return 500.0                      # ほとんど動けなかった
```

最小化ですので小さいほど良い値です。効果があるのは中間の2つの分岐です。衝突した候補がすべて同じ点数になると、失敗が平坦な領域になり、共分散の更新に使える材料がなくなって探索が漂います。止まった時点のペースで採点すると、この平坦な領域が傾きに変わります。3,000m地点まで速く走って壊れた候補は、最初のコーナーで飛んだ候補より上位に来ますので、分布は「失敗から遠ざかる」方向ではなく「速くて、あと少しで安全になる」領域へ動きます。

## 制御則と、手を入れた場所

制御は操舵系と速度系に分けてあります。探索空間を解釈できる状態に保ち、ある段階で悪化したときにどちらが原因か分かるようにするためです。

```
steer     = clip(angle·A/π − 不感帯(trackPos − 目標ライン, D)·B − Δ trackPos·4, −1, +1)
v_target  = clip(K_eff · track[9], 30, C)          # track[9] = 正面までの距離
throttle  = clip((v_target − speedX) · T, −1, +1)
```

これが全周共通の法則で、ここまでで122秒程度です。残りの14秒は、1組の定数では1周を賄えないと認めて、別の扱いをする場所を切り出すことで得ました。その場所は6つあり、二つの系に分かれます。以下の図の境界はすべて [`results/stage4_cma_8param_sector_s35.json`](results/stage4_cma_8param_sector_s35.json) から読んでいますので、コミットしてあるコントローラ以外を描くことはできません。

**操舵系**には、目標ラインをコース中央から外す窓を2つ置きました。s20+s21の複合コーナーと、s35のシケインです。窓の外では目標は中央のままで、作用するのはゲイン `A`、`B`、`D` だけです。

![走行ラインを変える区間](figures/corkscrew_zones_steering.svg)

図中の表記 — racing line＝走行ライン、chicane＝シケイン、start / finish＝スタート・フィニッシュ地点

**速度系**には4つの上書きがあります。毎周の走行距離500mまでで140km/hを超えていればブレーキを全開にする処理、s35の速度上限、最終ヘアピン手前のブレーキング区間で前方注視ゲインを下げる処理、そして3,305mから先を全開にする処理です。

![速度の法則を上書きする区間](figures/corkscrew_zones_speed.svg)

図中の表記 — post-start brake＝スタート後の減速、full brake＝ブレーキ全開、speed cap／ceiling＝速度上限、K_final braking＝進入側のゲイン低下、lookahead gain＝前方注視ゲイン、sprint＝フィニッシュ直線の全開

6つを合わせても1周3,608mのうち2,026mで、残りの1,582mは共通の法則のままです。どれも全周には及びません。これは意図したもので、全周に及ぶ介入は改善の帰属先が分からず、1周全体に触れずに外すこともできないためです。ここに置いた介入はどれも単独で切って測り直せます。

この段階で書き残しておきたい点が二つあります。

**不感帯 `D` は自明なパラメータではありませんでした。** 124秒付近で頭打ちになった原因は、直線での横位置センサのノイズが微修正を誘発するジグザグでした。横方向の誤差が `D` を下回る間は無視する形にしたところ、CMA-ES が `D ≈ 0.083` を見つけ、走行ラインが直線的になって約2秒短縮しました。仮説が先にあり、CMA-ES が担当したのは調整だけです。

**前方注視ゲインは全周で共通にできませんでした。** `K` は正面までの距離から速度を決めます。他の区間で速い値のままだと、半径18〜20mの最終ヘアピンへ速すぎる速度で進入します。区間を分けて進入側だけ `K_final` にすることで、他を遅くせずに解決しました。後述するs35の対処と同じ考え方を、別のコーナーに当てたものです。

## s35 の診断

プロジェクトの終盤で、他の場所では安全な速度のまま、ある1ヶ所でだけ**断続的に**衝突するようになりました。特定のコーナーでたまにしか出ない失敗は、試行錯誤で潰すと費用が跳ね上がりますので、推測では進めませんでした。

区間表はすでに `results/` にありましたので、衝突時に記録された `distRaced` を突き合わせました。結果はすべて一つの帯に収まりました。[コース](#コース)の図で赤く示した区間です。

| distRaced | 区間 | 方向 | 半径 | 円弧 |
|---|---|---|---|---|
| 2,441 m | s35-1 | 左 | 32 m | 52° |
| 2,461 m | s35-2 | 左 | 22 m | 52° |

連続する二つの低速左コーナー、つまりシケインです。CMA-ES が収束させた速度上限は長い直線に対しては正しく、この形状とは両立しませんでした。しかもコーナーが短いため、進入が速すぎることの代償は「常に遅い」ではなく「たまに壊れる」という形で現れていました。

対処は2,339〜2,510mの区間にだけ適用する速度上限 `C_s35 = 71.4 km/h` です。全体の減速でも、適応度への罰則項でもありません。どちらを選んでも、シケインの代償を残り3,400mの時間で払うことになります。この段階だけで116秒から108.692秒になりました。

上限は目標値ではなく天井として実装しています。シケインの内側で前方注視がすでに71.4 km/h より低い速度を要求している場面では、この上限は何もしません。その性質を固定するテストと、上限のかかる区間が記録された衝突の帯を覆っていることを確認するテストが入っています。

## 残差ネットワーク

最後の2秒は、調整済みのコントローラを置き換えるのではなく、その上に小さなネットワークを重ねて得ました。

```
throttle = clip( rule(obs) + 0.2 · NN(obs), −1, +1 )

obs(23) → Linear(32) → ReLU → Linear(32) → ReLU → Linear(1) → Tanh
```

設計上の判断は3つで、それぞれが深層強化学習を採らなかった理由に対応しています。

- **出力層をゼロ初期化しました。** 残差エージェントの最初の評価は、CMA-ESコントローラ**そのもの**です。開始時点の方策がすでに108.692秒ですので、初期状態で走れないという段階が存在しません。この性質は `test_zero_network_output_is_the_rule_controller` が固定しています
- **補正の大きさを制限しました。** 倍率0.2では、ネットワークの出力が振り切れてもスロットル指令は0.2しか動きません。速度の出し方を細かく直すことはできても、壊すことはできません
- **学習対象を33パラメータに絞りました。** [Augmented Random Search](https://arxiv.org/abs/1803.07055) で出力層だけを最適化します。評価1回がTORCSの実走行1周ですので、数時間で前に進む大きさまで探索空間を落とす必要がありました。6時間の微調整で106.630秒です

手で確認した3つの区間、つまりフィニッシュ前のスプリント、ブレーキング区間、スタート直後の減速は、ネットワークの制御対象から外し、後段で無条件に適用しています。すでに動いている挙動を学習し直すためにサンプルを使う理由はなく、安全側の挙動をネットワークに上書きさせる理由もありません。

学習ループは [`src/train_nn_ars.py`](src/train_nn_ars.py) にあります。

```bash
python src/make_track_map.py
python src/analyze_track.py --xml /path/to/torcs/tracks/road/corkscrew/corkscrew.xml
```

実際に走らせる場合は、主催者が指定したコンテナを使う手順が確実です。コンテナエンジンと約25GBの空き容量が必要になります。

```bash
bash container/build.sh
bash container/run.sh --race
```

2026-09-02にApple SiliconのMacで実測したところ、ウォームラップの最良タイムは**108.538秒**でした（記録上の基準値は108.692秒です）。手元のTORCSに対して走らせる手順を含め、詳しくは [`container/README.md`](container/README.md) と [Reproduction](README.md#reproduction) をご覧ください。

## 重みの公開と、まだ確かめられていないこと

106.630秒を出した走行の、残差ネットワークの重み（`models/nn_ars_s35_best.pt`）を**コミットしました**。`*.pt` が `.gitignore` に入っていたために4か月ほどバージョン管理の外にありましたが、失われてはおらず、開発に使っていたWindowsのマシンに残っていたものです。ARSが探索したのは出力層の33個で、その手前の層は、このプロジェクト自身のCMA-ESコントローラのスロットル指令を模倣学習させた重みです（同じファイルの中に入っていますので、走らせるだけならこのファイルだけで足ります）。詳細は [`models/README.md`](models/README.md) をご覧ください。

ファイルが本物かどうかは、SHA-256と、固定入力に対する出力の両方で確認できます。

```bash
python src/verify_weights.py --checksum-only   # バイト列のみ。Torch不要
python src/verify_weights.py                   # 読み込んで実際に計算させる
```

ただし、これで確かめられるのは**ファイルであって、タイムではありません**。106.630秒は2026年5月に開発マシンで計測した値で、それ以降、他のマシンでも固定コンテナの中でも再現していません。`container/` が固定しているのは108.692秒のCMA-ESの段階までで、こちらは別のマシン・別のアーキテクチャで108.538秒として5回再現できています。残差ネットワークの段階に同じ整備をするのが、[issue #1](https://github.com/sean-from-japan/torcs-racing-controller/issues/1) に残っている作業です。**106.630秒は記録された実測値であって、可搬な値ではありません。**

レポートに載せた途中の二つの値（8パラメータの区間版の116.062秒と、フィニッシュ直線のスプリントの112.404秒）にも、コミットされた成果物がありません。上の表からは外してあります。ラップタイムはTORCSのビルド、ブリッジへの変更、レース設定に依存しますので、公開した数値の近くには来ても同じ値にはならないとお考えください。

## 制約

- **環境をコンテナ化していませんでした。** 開発は1台の機械の上で、手作業で修正したTORCSに対して行いました。`container/` で環境を固定し、CMA-ESの段階は別のハードウェアでも走らせ直しましたが、残差ネットワークの段階はどこでも走らせ直せていません。106.630秒が1台のマシンでの計測にとどまっているのはそのためです。このプロジェクトで最初に直すならここです
- **学習した重みを4か月バージョン管理の外に置いていました。** `.gitignore` に `*.pt` を入れていたため、安く作り直せない唯一の成果物が、唯一追跡されていない成果物になっていました。マシンに残っていたので公開できましたが、これは運であって仕組みではありません。無視の設定は、そのファイルが実験結果かどうかで個別に決めるべきでした
- **1コース・1車種・1レース設定です。** すべてのパラメータは Corkscrew に合わせたもので、汎化の証拠は `results/` にありません
- **区間の境界は手で決めました。** 走行ラインの窓の端と残差の倍率0.2は手動で選び、探索したのはその内側の値だけです
- **適応度が1回の走行に基づいています。** 各候補は1エピソードのウォームラップの最良タイムで採点していますので、隣り合う段階の差の一部は実行ごとのばらつきです
- **判断の理由を結果と一緒に記録していませんでした。** ラップタイムは自動で残りましたが、各段階でパラメータを増やした理由は残りませんでした
- **学習用スクリプトは `controller.py` に合わせて書き直していません。** 各段階は最終的な制御則より前のもので、書き直すと実際に走らせたものと食い違います

一覧は [Limitations](README.md#limitations) にあります。
